DECODE-REPAIR MECHANISM
=======================
When ultralytics val scans a directory, it attempts to load each JPEG.
Source photos have a marginal header marker (JFIF/EXIF format) that
triggers PIL's "restore and save" repair path:
  "val: /path/to/G01P1__after.jpg: corrupt JPEG restored and saved"
The repair re-encodes the file and writes it back over the original.
Its SHA256 changes; its decoded RGB may differ slightly (JPEG is lossy).

The repair triggers on the ORIGINAL (source-bytes) JPEG. If val is run
a second time on the already-repaired files, the message does not
appear again (the header is now valid). So "every val run mutates the
export" is only true for the first val on a given set of source-bytes
JPEGs. Re-running val on already-repaired JPEGs does not mutate them
further.

The original E0 training run's console output was not preserved to a

val.cache FILE
==============
`yolo_export_at_E0_time/labels/val.cache` was produced by ultralytics
when val scanned the labels directory. It contains the paths, image
sizes, and label data for the 8 val images as they existed at the time
of that val run. The paths point at `yolo_export/...` (not
`yolo_export_at_E0_time/...`) because ultralytics was invoked with
`data=yolo_export/dataset.yaml` at that time; the cache records
absolute paths from that invocation. It is undocumented in earlier
versions of this file and is preserved as-is as evidence of the val
scan. No train.cache was created because training does not use a val
scan in the same way. If the cache is deleted and val is re-run, it
will be regenerated.

Why the two dataset_yaml values differ
--------------------------------------
artifact.json top-level `dataset_yaml` = /home/wyc/.../yolo_export/dataset.yaml
resolved_config_at_training.data.dataset_yaml = data/exports/yolo/dataset.yaml

trainer.py writes the SAME variable into both files at training time. That original
trainer output was:
  artifact.json.dataset_yaml = resolved_config.json.data.dataset_yaml = data/exports/yolo/dataset.yaml
(the value from baseline.json's data.dataset_yaml field, which was a placeholder that
was later overridden by --dataset on the CLI).

The trainer DID NOT write /home/wyc/... into either file. The /home/wyc/... value in
artifact.json was written by an earlier ad-hoc edit (now preserved as a POST-HOC
correction, not trainer output). The canonical effective path used at training time
was passed via --dataset and is separately recorded in this provenance file (see
"REPRODUCTION COMMANDS" above — the CLI invocation includes
--dataset /home/wyc/.../yolo_export/dataset.yaml).

Current state:
  artifact.json.dataset_yaml = /home/wyc/.../yolo_export/dataset.yaml  (effective CLI override)
  resolved_config_at_training.data.dataset_yaml = data/exports/yolo/dataset.yaml  (config file value)

Both are accurate records of different things.

Why top-level inference (0.20/0.35) differs from embedded resolved_config.inference
-------------------------------------------------------------------------------------
There are three "inference" views in the current package:
1. artifact.json.confidence_threshold / nms_iou_threshold = 0.20 / 0.35 (FROZEN release values)
2. artifact.json.resolved_config.inference = 0.20 / 0.35 (matches #1 by design — both frozen)
3. artifact.json.resolved_config_at_training.inference = 0.25 / 0.45 (historical training-time values)

#1 and #2 are the frozen release settings; they match because both were updated to
frozen values in commit 6b6f9b6.
#3 is the training-time config preserved separately by finalize_artifact.py.

The ORIGINAL run config was 0.25 / 0.45 (from baseline.json at training time).
The FINAL RELEASE config is 0.20 / 0.35 (from validation-only threshold tuning).
